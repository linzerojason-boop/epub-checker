## 一、总体结论

**首轮（v3.13）**：重构方向正确，上一份审查报告的 P0/P1/P2/P3 绝大多数已修好，且没有在修复中引入数据损坏（所有写盘功能都被 `verify_epub` 兜住）。但当时发现 **合并 EPUB 从界面 100% 用不了**（进度回调签名不匹配）、替换封面后留两条 `properties="cover-image"`、以及合集报告两处误导性文案。

## 二、首轮失败项与 v3.14 修复验证

> 本节记录的都是 **v3.13 首轮**的现象；每条开头给出 v3.14 的复测状态与修法。

### P0-N1 合并 EPUB 界面必失败：进度回调签名不匹配　（v3.14 已修）

> v3.14 状态：**已修复**。引擎新增 `_notify(progress, done, total, text)`，用 `inspect.signature` 数位置参数个数：≥3 传 `(done,total,text)`、2 个传 `(done,total)`、1 个传 `text`，界面原样保留 `prog(i, n, text)` 即可。复测 T16.1 → 「合并成功」，产物 `verify` 0 问题、53 项 manifest、16 条目录。

**现象**：合并页加 2 本、标题和输出路径都正常（`btn_start` 已亮），点「开始合并」→ 底栏「失败」，结果框：

```
合并失败：TypeError: MergeDialog._run.<locals>.work.<locals>.prog() missing 2 required positional arguments
```

**取证**：引擎直调同一对书 → 成功，3.5 MB，`verify_epub` 0 问题、manifest 无重复 id、目录 16 条。

**根因**（两侧契约不一致）：

```python
for i, p in enumerate(paths, 1):

        progress("正在复制第 %d/%d 本：%s" % (i, len(paths), os.path.basename(p)))
...

        progress("正在自检…")            # :1048

```


### P2-N2 替换封面后仍留两条 `properties="cover-image"`　（v3.14 已修）

> v3.14 状态：**已修复**。`patch_opf` 在插入新封面前先遍历 manifest，把旧条目上的 `cover-image` 属性摘掉（文件保留，避免删掉被正文引用的图）。复测：输出只剩 1 条 `properties="cover-image"`（`images/cover.jpg`），`cover_hrefs()` 也只返回这一张，`verify` 0 问题。

**现象**：对《三日间的幸福》（原封面 `Image00000.jpg`）替换封面 → 输出自检 0 问题，但 manifest 是：

| id | href | properties |
| --- | --- | --- |
| cover-image | `Image00000.jpg` | **cover-image** |
| cover-image2 | `images/cover.jpg` | **cover-image** |

以及 `<meta name="cover" content="cover-image2"/>`、`cover.xhtml` → `images/cover.jpg`（新图，显示正确）。

**影响**：
- EPUB3 规范要求 `cover-image` 属性**最多一条**，两条即不合规，但 `verify_epub` / `check_single` 都不报（静默）。
- `core.cover_hrefs()` 返回两张 → 再打开这本书时「已有封面」提示会写「Image00000.jpg、cover.jpg」，用户会以为加封面失败、重复操作。

上一版的「manifest 重复 id」确实修好了（`uniq()` 生效，变成 `cover-image` / `cover-image2`），但**属性没有转移**——去重只解决了 id 唯一，没解决语义唯一。

**修法**：`patch_opf` 里替换封面分支，给新 item 赋 `properties="cover-image"` 之前，把其余 item 上的 `cover-image` 属性清掉；旧封面图可保留为普通图片或从 manifest 移除（保留更安全，避免删掉被正文引用的文件）。

### P2-N3 合集检查结论把「无法比对」算成「已找到」　（v3.14 已修）

> v3.14 状态：**已修复**。复测输出：`说明 : 有 1 本分册无法比对（未计入缺失统计）`、`结论 : 未发现缺失，但并非所有分册都参与了比对`。

**现象**：合集 = 污秽 1-5 合集（818 页漫画），分册 = 污秽(1) + 你好，世界（文字书）。

```
[1/2] 污秽不堪的你最惹人怜爱 (1) …   页数 152, 匹配 152, 缺失 0
[2/2] 你好，世界 …                  [警告] 合集是 image, 分册是 text, 比对可能无意义
                                    (合集无文字, 无法比对)
结论 : 所有分册内容均已在合集中找到, 未发现缺失
```

第 2 本**一页都没比对**，结论却说「所有分册内容均已在合集中找到」。这是最容易被用户当成「合集已齐」的错误结论。

**修法**：结论行按参与比对的分册统计，例如：

```
结论 : 已确认包含 1/2 本；1 本因类型不符未能比对（你好，世界：text vs image）
```

### P3-N4 合集报告把「未被分册匹配的页」称作「疑似重复页」　（v3.14 已修）

> v3.14 状态：**已修复**。复测输出 `合集里未被任何分册匹配的页: 666（其中与另一页几乎相同: 12）`，把「未匹配」和「真重复」分开计数，标题里不再出现「疑似重复页」。

```
合集未被任何分册匹配的页(疑似重复页): 666
   cover.jpg  (与 kcc-0001-kcc-x.jpg 相同)      ← 真重复
   kcc-0002-kcc-x.jpg  (最接近 kcc-0140-kcc-x.png, MAD 42.5)   ← 只是「最像」
```

只提供 1/5 卷时 666 页没被匹配，是**正常现象**（它们在没提供的第 2-5 卷里），不是重复页。真重复的判定阈值是 `PAGE_DUP_MAD=2.0`（MAD 25-64 的那批显然没到），但标题把两者混在一起，标题建议改成「合集未被分册匹配的页（含疑似重复）」，并只对 MAD ≤ 2 的条目标「相同」。

## 五、补充观察（当前遗留，均不影响功能）

1. **合并会静默继承源书的缺陷**。用《含羞草的告白3》合并，产物 `check_single` 报「断链图片 1：`../OEBPS/6.jpg`」——这是源书自带的问题，合并只是原样搬运（正确处理），但界面只显示「合并成功」，用户不会知道新书里有断链。建议：合并完成后把 `verify + 各分册 check_single` 的问题条数汇总到 `txt_result`，一行提示即可。
2. **合并进度条观感**。`progress.setMaximum(len(ps)+1)`，引擎现在只回调「第 i/n 本」和「自检」两次，进度条基本不满；可在 `prog(i, n, text)` 里顺手 `setValue(n)` 让进度条按册推进。
3. **`_add_paths` 里 docstring 位置错误**（`epub_gui_qt.py:1556`）：`if paths: remember_dir(paths[0])` 写在了三引号之前，函数文档字符串变成一条无用的字符串表达式。功能无影响，属代码整洁问题。

> 首轮报告里的第 4 条（`epub_core.py` 门面残留 200 行空行 + 重复 re-export）**v3.14 已清理**：现在 55 行、0 空行。

## 六、最小回归集合（每次发版跑这 5 条，约 40 秒）

1. 合并页 2 本 → 出文件、`verify` 0；
2. 替换封面 → manifest 里 `cover-image` 只 1 条、`cover_hrefs` 只 1 张；
3. 合集 + 1 本类型不符分册 → 结论写明「并非所有分册都参与了比对」；
